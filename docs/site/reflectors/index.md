# Reflector directory

A digital-voice reflector directory for **D-Star, M17, YSF, NXDN, P25 and URF**,
served as static JSON. No API key, no account, no rate limit — it is a file on a
CDN.

```bash
curl -s https://rcludwick.github.io/hamcall-db/api/v1/index.json
curl -s https://rcludwick.github.io/hamcall-db/api/v1/reflectors.json
curl -s https://rcludwick.github.io/hamcall-db/api/v1/reflectors/dstar.json
```

The full contract, including every field and the extensibility rules, is the
[API reference](api.md).

## The four endpoints

| Endpoint | What it is |
|---|---|
| [`api/v1/index.json`](../api/v1/index.json) | Service manifest: which networks exist, how many rows each has, how fresh they are. |
| [`api/v1/reflectors.json`](../api/v1/reflectors.json) | Every reflector, every network — the primary endpoint. |
| `api/v1/reflectors/{network}.json` | One network on its own. |
| [`api/v1/openapi.json`](../api/v1/openapi.json) | The contract, machine-readable. Generated by the build, so it cannot drift from the data. |

Most clients want `reflectors.json`. The per-network files exist for **failure
isolation**: upstreams break independently, and a D-Star-only client should not
re-download 1,400 YSF rows to find out nothing changed.

## The entry shape

Every entry is a common **envelope** — what you search and display — plus a
discriminated **`dial`** object, which is what you connect with and differs per
protocol because the protocols genuinely differ.

```json
{
  "network": "dstar",
  "id": "XLX836",
  "name": "XLX836",
  "aliases": ["XRF836"],
  "description": "Welcome",
  "country": "USA",
  "dashboard": "http://xlx.n7mky.com",
  "source": "xlx",
  "dial": {
    "kind": "dextra",
    "host": "45.56.69.219",
    "port": 30001,
    "callsign": "XRF836"
  }
}
```

Switch on `dial.kind` — `dextra`, `m17`, `ysf`, `nxdn`, `p25`, `urf`. **A kind
you do not recognise should be shown, never dialled.** That is the extension
mechanism: a new network ships as a new kind, and older clients degrade to
"listed, not offered" rather than breaking.

`dial.callsign` is the name the reflector answers to *on the air*, which is not
always its directory name — an XLX reflector is listed as `XLX836` but a DExtra
client must put `XRF836` in its RPT1/RPT2 header. The same name appears in
`aliases`, so a user typing either form finds the entry.

!!! danger "XRF and XLX are not the same reflectors"

    They share a numbering scheme and nothing else. Measured 2026-08-26 by
    resolving DVRef's XRF hostnames against the XLX registry's addresses, **13 of
    14** sampled `XRF###`/`XLX###` pairs pointed at entirely different servers:
    `XRF002` is `xrf002.dstar.club`, while `XLX002` is a host in China.

    Both are published under their own ids and are **never** merged. Collapsing
    them would send an operator to a reflector on another continent.

## Refresh policy

The files are rebuilt **nightly**, but they carry `client_refresh_days: 7`.

**Please cache for a week.** Reflector addresses move on a scale of weeks, so
polling harder costs everyone bandwidth and buys nothing. The two numbers are
different knobs on purpose: the build is nightly so the data is never more than a
day stale, and clients are asked to back off so a static host is not hammered by
every install on earth.

`generated` reflects the **data**, not the build. A rebuild that finds nothing
new produces byte-identical files, so a client comparing `generated` sees
movement only when something actually moved.

A network whose upstream fails, or whose row count collapses, keeps its previous
file rather than publishing a regression. Upstream is volunteer-run and offers no
SLA — an outage there must not blank out every client's reflector picker.

## Licence

The licence depends on where each row came from, and every row says which
applies in its own `license` field.

| Rows | `source` | Row `license` | What that means |
|---|---|---|---|
| M17, YSF, NXDN, P25, URF and DMR servers, and the DMR talkgroup files | `dvref` | `CC-BY-4.0` | CC BY 4.0. Commercial use is permitted; attribution and a statement of modification are required. |
| D-Star reflectors from the XLX registry | `xlx` | `none-stated` | The registry publishes no licence. The rows are redistributed as facts, and no rights are granted beyond what the registry provides. |
| Standalone XRF reflectors from the Pi-Star DExtra host file | `dextra` | `none-stated` | Pi-Star publishes no licence. Same treatment as the XLX rows. |

D-Star rows can also carry REF and DCS names in `aliases`. Those names come
from the Pi-Star DPlus and DCS host files, which state no licence either, and
the row records that with `alias_source: "pistar"`.

hamcall-db's own contributions (the schema, the selection and the derived
fields) are CC BY 4.0.

Each file's top-level `license` sums up its rows. A file whose rows are all
CC BY (`m17.json`, `ysf.json`, `nxdn.json`, `p25.json`, `urf.json`, `dmr.json`
and the talkgroup files) says `"CC BY 4.0"`. A file holding any `none-stated`
rows (`dstar.json`, `reflectors.json` and `index.json`) says
`"mixed — see per-row license and NOTICE"` and carries a `rights` note. Every
file also carries `attribution` and `modifications` inline, so the terms cannot
get separated from the data. If you need a set that is wholly CC BY, keep only
the rows whose `license` is `CC-BY-4.0`.

When you redistribute the directory, reproduce each attribution line that
applies to the rows you pass on (all four, for the files whole). Only the DVRef
line is a CC BY 4.0 obligation; the other three credit sources that state no
licence.

```
Reflector data provided by DVRef — https://dvref.com/
XLX reflector data from the XLX registry maintained by Luc Engelmann, LX1IQ
(http://xlxapi.rlx.lu/).
Standalone XRF reflector data from the Pi-Star DExtra host file
(http://www.pistar.uk/downloads/DExtra_Hosts.txt).
REF and DCS reflector names from the Pi-Star DPlus and DCS host files
(http://www.pistar.uk/downloads/), which compile them from dstargateway.org
and xreflector.net DNS.
```

None of this is the licence on the [callsign dataset](../callsigns.md). See
[Licensing](../about/licensing.md) for why the two must stay apart.
